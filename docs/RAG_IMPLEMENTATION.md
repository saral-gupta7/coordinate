# Coordinate Course-Source RAG Implementation

## 1. What the feature does

Coordinate lets an authenticated learner attach a private, text-based PDF to a
specific course. The backend extracts page text, splits it into overlapping
semantic chunks, generates Gemini embeddings, and stores the chunks in the
project's existing PostgreSQL database through the `pgvector` extension.

When the learner generates a chapter lesson, the Lesson Builder derives a
retrieval query from the chapter title, description, and learning outcomes. It
retrieves only sufficiently similar chunks belonging to that user and course,
adds those chunks to the LangGraph state, and asks the lesson model to ground
source-backed claims in them. The generated lesson can carry inline source IDs
and structured citations containing the document ID, chunk ID, filename, and
page number.

The implementation provides:

- Authenticated PDF upload from the course workspace.
- File-size, file-extension, PDF-signature, page-count, encryption, and
  extractable-text validation.
- Page-preserving text extraction with `pypdf`.
- Recursive chunking with configurable chunk size and overlap.
- Gemini retrieval-document and retrieval-query embeddings through LangChain.
- Persistent 768-dimensional vectors in PostgreSQL/pgvector.
- An HNSW cosine-similarity index.
- User- and course-scoped similarity retrieval.
- A configurable top-k limit and minimum similarity threshold.
- A `retrieve_references` node in the existing LangGraph Lesson Builder.
- Page-level structured citation metadata.
- Prompt-injection separation: uploaded text is explicitly treated as
  untrusted reference data rather than executable instructions.
- Citation validation during the lesson-review node.
- Graceful degraded operation when no sources exist or retrieval is
  temporarily unavailable.
- Listing and deletion of private course sources.

## 2. Why this architecture fits Coordinate

Coordinate already uses LangGraph for explicit, inspectable course-planning
and lesson-building workflows. RAG is therefore implemented as a focused
retrieval service and a deterministic graph node, not as a separate agent.

This follows the project's existing rule:

- The Lesson Builder is the agent because it owns the user-facing goal of
  producing a complete lesson and quiz.
- `retrieve_references` is a node because it performs one step toward that
  goal.
- PDF extraction, chunking, embedding, and vector search are services/tools
  called by that node.

The implementation reuses PostgreSQL rather than adding an unrelated vector
database. This keeps user, course, document, and vector ownership within one
transactional data platform and makes tenant filtering explicit.

## 3. End-to-end flow

### 3.1 Upload and indexing

```text
Authenticated browser
  -> Next.js course document proxy
  -> FastAPI internal RAG route
  -> bearer-token and X-User-Id verification
  -> verify Course.id belongs to User.id
  -> validate PDF and size limit
  -> extract selectable text per page
  -> recursively split each page
  -> embed chunks with Gemini
  -> store document metadata and vectors
  -> return page count, chunk count, and ready status
```

The upload is synchronous in the current scope. A document starts in
`PROCESSING`, becomes `READY` after every chunk is stored, and becomes `FAILED`
with a bounded error message if embedding or persistence fails.

### 3.2 Retrieval and lesson generation

```text
START
  -> prepare_context
  -> retrieve_references
       query = chapter title + description + outcomes
       embed query with the same Gemini model/dimensions
       filter by user_id and course_id
       cosine search with threshold and top-k
  -> draft_lesson
       source blocks labeled S1..Sn
       inline source markers
       structured page citations
  -> generate_quiz
  -> review_lesson
       verify supported source attributions
  -> prepare_response
  -> END
```

When no chunk clears the configured threshold, the node returns an empty
source list. The lesson workflow remains available, but its prompt explicitly
forbids fabricated private-document citations.

## 4. Data model

### `KnowledgeDocument`

Stores one user-uploaded course source:

| Field | Purpose |
| --- | --- |
| `id` | Stable document ID generated by the backend |
| `userId` | Owner used for tenant isolation |
| `courseId` | Course boundary used for retrieval |
| `filename` / `mimeType` | Display and validation metadata |
| `status` | `PROCESSING`, `READY`, or `FAILED` |
| `pageCount` / `chunkCount` | Inspectable ingestion result |
| `errorMessage` | Bounded failure reason |
| timestamps | Upload and update audit metadata |

### `KnowledgeChunk`

Stores one retrievable unit:

| Field | Purpose |
| --- | --- |
| `documentId` | Cascading relation to the uploaded source |
| `userId` / `courseId` | Denormalized filters applied before retrieval |
| `filename` / `pageNumber` | Human-readable citation metadata |
| `chunkIndex` | Stable ordering within the document |
| `content` | Extracted source text |
| `embedding` | `vector(768)` used for cosine search |

The migration enables `pgvector` and creates an HNSW index with
`vector_cosine_ops`. Deleting a document cascades to all of its chunks.

## 5. Chunking and embeddings

Defaults are intentionally configurable:

| Setting | Default | Reason |
| --- | ---: | --- |
| `RAG_CHUNK_SIZE` | 1200 characters | Enough local context for educational text |
| `RAG_CHUNK_OVERLAP` | 180 characters | Preserves ideas split at chunk boundaries |
| `RAG_RETRIEVAL_K` | 5 | Small, reviewable context window |
| `RAG_SIMILARITY_THRESHOLD` | 0.35 | Suppresses weakly related chunks |
| `EMBEDDING_DIMENSIONS` | 768 | Lower storage/latency than 3072 dimensions |
| `RAG_MAX_FILE_SIZE_MB` | 8 MB | Bounds request memory and embedding cost |
| `RAG_MAX_PDF_PAGES` | 100 | Bounds synchronous ingestion work |

`GoogleGenerativeAIEmbeddings` automatically uses retrieval-document task
semantics for `embed_documents` and retrieval-query semantics for
`embed_query`. Index and query vectors use the same model and dimensionality;
mixing embeddings from different models in one index is not supported.

## 6. API surface

All endpoints require the existing internal bearer token plus `X-User-Id`.
The Next.js API routes derive those headers from the authenticated session; the
browser never receives the internal service token.

| Method | Route | Purpose |
| --- | --- | --- |
| `POST` | `/internal/rag/courses/{course_id}/documents` | Validate, index, and store a PDF |
| `GET` | `/internal/rag/courses/{course_id}/documents` | List the user's sources for one course |
| `DELETE` | `/internal/rag/courses/{course_id}/documents/{document_id}` | Delete a source and its chunks |
| `POST` | `/internal/rag/courses/{course_id}/search` | Inspect scoped retrieval results |

The search endpoint accepts:

```json
{
  "query": "How do transactions guarantee atomicity?",
  "top_k": 5
}
```

Each result exposes similarity, source filename, page number, chunk index,
document ID, and chunk ID so retrieval behavior is debuggable.

## 7. Security and reliability controls

### Tenant isolation

- The backend verifies that the requested course belongs to `X-User-Id`
  before creating or listing documents.
- Chunk rows contain both `userId` and `courseId`.
- Every similarity query filters on both fields before ordering by vector
  distance.
- Document deletion also requires the same user and course IDs.

### Upload controls

- Only `.pdf` filenames are accepted.
- File bytes must start with the PDF signature.
- Upload size and page count are bounded.
- Password-protected PDFs are rejected.
- PDFs without selectable text are rejected with a clear OCR limitation.
- Path components are removed from uploaded filenames.

### Prompt-injection handling

Retrieved chunks are enclosed in explicit `<source>` blocks. The generation
prompt says that content inside those blocks is reference data and that any
instructions contained in a document must be ignored. Source-backed claims
must use supplied IDs; the review node checks for fabricated or unsupported
attributions.

### Failure behavior

- A failed ingestion is stored as `FAILED` instead of appearing complete.
- Embedding dimensionality is checked before persistence and retrieval.
- If retrieval is unavailable during lesson generation, the graph records a
  degraded-mode trace and continues with the approved course context.
- No-source generation is explicitly forbidden from inventing private-source
  citations.

## 8. Frontend behavior

The course workspace contains a **Private course sources** section. A learner
can upload a PDF, see its page/chunk counts and indexing status, and delete it.
The browser talks only to authenticated Next.js proxy routes. React Query
refreshes the source list after uploads and deletions, while Sonner reports
success or actionable validation failures.

Once a source is ready, subsequent lesson generation for that course
automatically uses it when the retrieved chunks are relevant to the selected
chapter. No extra checkbox or manual prompt construction is required.

## 9. Local setup and deployment

1. Use the same PostgreSQL `DATABASE_URL` in `frontend/.env` and
   `backend/.env`.
2. Ensure the database account can run `CREATE EXTENSION vector`, or enable
   `pgvector` through the managed provider first.
3. Apply the Prisma migration:

   ```bash
   cd frontend
   pnpm exec prisma migrate deploy
   pnpm exec prisma generate
   ```

4. Sync backend dependencies:

   ```bash
   cd ../backend
   uv sync
   ```

5. Configure the RAG settings shown in `backend/.env.example`.
6. Start FastAPI and Next.js normally.

The vector dimension in the migration is 768. Changing
`EMBEDDING_DIMENSIONS` therefore requires a deliberate schema migration and
re-indexing existing chunks.

## 10. Verification

Backend tests cover:

- invalid PDF rejection;
- page metadata preservation through recursive splitting;
- stable chunk ordering;
- safe filename normalization;
- 768-dimensional embedding validation;
- propagation of `user_id` and `course_id` to every stored chunk;
- tenant filters, top-k, and similarity-threshold forwarding;
- inspectable source metadata added to the lesson prompt;
- invalid chunk-size/overlap configuration.

Run:

```bash
cd backend
PYTHONPATH=. uv run pytest

cd ../frontend
pnpm typecheck
pnpm lint
pnpm build
```

## 11. Current limitations and next iterations

The current implementation deliberately keeps the first production slice
defendable:

- Ingestion is synchronous; large-document processing should move to a
  background queue later.
- Text-based PDFs are supported; scanned PDFs need a sandboxed OCR pipeline.
- Retrieval uses dense cosine similarity only; hybrid lexical/vector search
  and reranking are future improvements.
- The similarity threshold should be tuned against a labeled evaluation set
  rather than assumed universal.
- Production observability should add retrieval latency, embedding cost,
  retrieved-chunk count, citation coverage, and abstention metrics.
- A course-aware Tutor Agent can reuse the same retriever after its chat and
  memory model is implemented.

## 12. Resume-ready description

The implementation supports this factual resume bullet:

> Integrated course-scoped RAG into a LangGraph lesson workflow using Gemini
> embeddings, recursive PDF chunking, and PostgreSQL/pgvector retrieval,
> grounding generated lessons with page-level citations and user-isolated
> document access.

Do not add retrieval accuracy, latency, cost, or citation-quality numbers until
they are measured on a versioned evaluation dataset.
